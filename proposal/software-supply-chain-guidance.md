# 외부 프로그램과 패키지를 확인하고 사용할 수 있도록

기능이 잘 동작한다는 이유만으로 출처와 용도를 확인하지 않은 프로그램이나 패키지(다른 사람이 만든 기능을 설치해 사용하는 묶음)를 가져다 써서는 안 됩니다. 설치하거나 서비스를 배포할 때마다 검토 없이 최신 버전을 받아 쓰도록 설정하는 것도 주의가 필요합니다. 반면 이미 알려진 보안 문제를 고치는 업데이트는 제때 적용해야 합니다.

지침에는 무엇을 가져다 쓰는지 확인하고, 새 버전의 적용 여부를 판단하며, 필요한 보안 패치를 놓치지 않는 방법을 함께 담으면 좋겠습니다. 공급 업체의 지원을 받는 제품과 AI로 직접 만든 도구 모두, 사용 현황과 이후 관리까지 살펴보자는 취지입니다.

## 가져다 쓰는 프로그램과 패키지의 출처를 확인합니다

인터넷 게시글에 첨부된 실행파일(프로그램을 실행하거나 설치하는 파일, 예: `.exe`)이나 AI가 추천한 패키지는 기능 설명만 보고 바로 사용하지 않도록 안내할 필요가 있습니다. 누가 만들었는지, 왜 필요한지, 제작자가 안내하는 배포 경로에서 받는지, 계속 관리되고 있는지 확인해야 합니다. 이름이 유명한 제품과 비슷하다는 이유만으로 같은 제품이라고 믿어서는 안 됩니다.

프로그램 안에 함께 들어오는 구성요소도 확인 대상입니다. 로그인이나 파일 처리를 위해 사용한 라이브러리(기능을 모아 둔 코드)가 또 다른 라이브러리를 가져다 쓰면, 직접 선택하지 않은 구성요소까지 설치될 수 있습니다. 그중 하나에 보안상 약점인 취약점이 있으면 이를 사용하는 서비스에도 영향을 줄 수 있습니다.

이처럼 프로그램에 들어가는 부품부터 제작·배포·업데이트까지 이어지는 과정을 소프트웨어 공급망이라고 합니다. 원래 있던 취약점의 영향을 받을 수도 있고, 누군가 제작·배포 과정에 악성 기능을 끼워 넣는 공급망 공격을 당할 수도 있습니다. 내가 직접 작성한 부분만 살펴봐서는 놓칠 수 있는 위험입니다.

오픈소스처럼 소스코드(프로그램을 작성한 내용)가 공개되어 있어도 실제 배포파일에 문제가 없다고 단정할 수는 없습니다. 공개된 코드에 문제가 없더라도 설치파일을 만들거나 패키지로 묶고 배포하는 과정에서 악성 기능이 들어갈 수 있습니다. 공식 경로에서 받는 것은 기본적인 확인이지만, 그 배포 과정 자체의 문제까지 없다는 뜻은 아닙니다.

모든 이용자에게 코드를 직접 분석하라고 요구하기보다는, 사용하는 프로그램과 패키지의 출처를 확인하고 배포 취소나 악성 버전 안내가 나왔을 때 해당 여부를 알아볼 수 있도록 설명하면 좋겠습니다.

## 최신 버전이 검토 없이 운영에 반영되지 않게 합니다

서비스를 배포할 때마다 패키지의 최신 버전을 자동으로 받아 쓰면, 어제 확인한 구성과 오늘 실제로 운영하는 구성이 달라질 수 있습니다. 개발자가 직접 작성한 코드를 바꾸지 않았더라도 새로 받아 온 패키지에서 오류가 생기거나 악성 기능이 실행될 수 있습니다.

지침에는 확인한 버전을 사용하고, 다른 버전으로 바꿀 때는 변경 내용과 서비스에 미칠 영향을 살펴보는 기준이 필요합니다. 자동화된 설치·배포에서도 검토를 거친 업데이트가 반영되도록 하고, 무엇이 바뀌었는지 확인할 수 있어야 합니다.

보안 수정이 아닌 새 기능이나 일반적인 개선은 배포 직후 바로 적용하기보다, 일정 시간 동안 문제 보고와 배포 철회 여부를 살펴본 뒤 적용할 수 있습니다. 일부 패키지 관리 도구(패키지를 설치하고 업데이트하는 프로그램)는 공개된 뒤 정해진 시간이 지난 버전만 설치 대상으로 고르는 기능을 제공합니다. 사용하는 도구에서 이 기능이 적용되는지와 예외가 무엇인지도 확인해야 합니다.

다만 오래됐다고 안전한 것은 아닙니다. 확인한 버전을 계속 사용한다는 원칙이 업데이트를 하지 않는 이유가 되어서도 안 됩니다. 새 버전을 무조건 따라가지 않으면서 필요한 변경은 놓치지 않는 관리가 필요합니다.

## 보안 패치는 일반 업데이트와 구분해 제때 적용합니다

보안 패치는 알려진 취약점을 고치는 업데이트입니다. 새 버전을 기다려 보는 원칙을 보안 패치에도 일률적으로 적용하면, 공격에 이용될 수 있는 약점을 그대로 둔 채 기다리게 됩니다. 한 버전에 새 기능과 보안 수정이 함께 포함될 수도 있으므로 변경 내용을 확인해야 합니다.

예를 들어 편집 기능이 추가된 버전은 잠시 지켜볼 수 있지만, 사용 중인 게시판에 다른 사람이 무단으로 접근할 수 있는 문제를 고친 버전이라면 같은 대기 기간을 기계적으로 적용해서는 안 됩니다. 공식 보안 수정인지, 우리 시스템에도 해당하는지, 실제 공격에 악용되고 있는지 확인해 우선순위를 정해야 합니다.

긴급한 패치는 필요한 테스트와 복구 준비를 거쳐 신속히 적용할 수 있도록 하고, 설치 대기 설정이나 정기 업데이트 일정 때문에 조치가 늦어지지 않게 예외 절차도 마련할 필요가 있습니다. 검토와 적용을 담당할 사람이 누구인지 함께 정하면 도움이 됩니다.

바로 적용하기 어렵다면 제작자가 안내하는 임시 대응을 확인하고, 영향을 받는 기능이나 외부 접근을 제한할 수 있는지 검토합니다. 미뤄 둔 항목에는 이유와 조치 담당자, 다음 확인 시점을 남겨야 합니다. 파일을 받거나 업데이트를 예약한 것만으로 완료로 보지 않고, 실제 운영 시스템에 적용됐는지와 서비스가 정상으로 동작하는지까지 확인하도록 안내하면 좋겠습니다.

## 유료 솔루션을 선택할 때는 보안 지원도 함께 확인합니다

기업이 유료 솔루션을 사용하는 이유 중 하나는 필요한 기능과 함께 보안 패치, 취약점 대응 안내와 기술 지원을 받을 수 있기 때문입니다. 문제가 알려졌을 때 해당 여부를 문의하고, 어떤 버전으로 바꿔야 하는지나 업데이트 중 주의할 점을 안내받을 수 있다면 운영 부담을 줄이는 데 도움이 됩니다.

따라서 도입할 때 기능과 가격뿐 아니라 어떤 지원을 언제까지 받을 수 있는지도 확인하도록 제안합니다. 보안 패치 제공 기간과 조건, 긴급한 문제의 문의 경로, 업데이트 적용을 누가 맡는지, 지원이 끝나면 어떻게 대응할지 같은 내용입니다. 실제 제공 범위는 제품과 계약에 따라 다릅니다.

유료라는 이유만으로 문제가 생기지 않는 것은 아니며, 업체가 패치를 제공해도 우리 시스템에 적용하는 일은 따로 남을 수 있습니다. 오픈소스 제품에도 유료 지원이 제공되는 경우가 있으므로, 유료와 오픈소스를 반대 개념으로 나누기보다 관리와 지원을 어떻게 확보할지 설명하면 좋겠습니다.

## AI로 만든 도구도 사용 현황과 관리 대상에 포함합니다

보안 요구가 엄격한 조직에서는 설치하거나 실행할 수 있는 프로그램을 정하고, 새 프로그램은 확인을 거쳐 사용하도록 관리하기도 합니다. 어떤 프로그램이 어디에서 사용되는지 파악하고, 불필요하거나 확인되지 않은 프로그램이 들어오는 일을 줄이려는 것입니다.

하지만 AI에게 필요한 기능을 설명해 프로그램을 만드는 방식이 늘어나면, 기존 설치 프로그램 목록만으로는 현황을 놓칠 수 있습니다. 허용된 개발 도구로 업무용 프로그램을 직접 만들더라도, 그 안에서 별도의 패키지를 내려받아 사용할 수 있기 때문입니다. 기능이 동작하는지만 확인했다면 만든 사람도 무엇이 함께 설치됐는지 모를 수 있습니다.

예를 들어 AI로 만든 파일 정리 도구가 여러 패키지를 사용하지만 회사의 관리 목록에는 개발 도구만 등록되어 있을 수 있습니다. 나중에 그 패키지에서 취약점이 알려져도, 해당 도구를 누가 어디에서 사용하는지 모르면 확인과 패치가 어려워집니다. 조직의 점검 절차 밖에서 실행되면 출처를 확인하지 않은 구성요소에 노출될 수도 있습니다.

지침에는 구매하거나 내려받은 완성 제품뿐 아니라 직접 만든 도구와 그 안에 쓰인 패키지도 관리 범위에 포함하도록 제안합니다. 어떤 용도로 어디에서 사용하는지, 어떤 구성요소와 버전을 쓰는지, 출처가 어디인지, 보안 업데이트를 누가 확인하고 적용할지 알아볼 수 있어야 합니다.

AI가 기능을 빠르게 만들어 주어도 이후의 관리까지 자동으로 해결되는 것은 아닙니다. 새 도구를 쓰기 전에 필요한 확인과 담당자를 정하고, 지원이나 관리가 끊긴 도구는 교체하거나 사용을 끝낼 수 있도록 안내할 필요가 있습니다.
