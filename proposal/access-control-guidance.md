# 권한에 맞는 정보와 기능만 이용할 수 있도록

로그인은 누구인지 확인하는 과정이고, 권한은 그 사람이 어떤 정보를 보고 어떤 일을 할 수 있는지 정하는 규칙입니다. 일반 회원이 로그인했다는 이유만으로 다른 회원의 주문을 보거나 관리자 기능을 이용할 수 있어서는 안 됩니다.

"누가, 누구의 자료를, 어느 항목까지 보고 바꿀 수 있는가"를 쉬운 사례로 설명하는 안내와 점검표를 제안합니다. 비전문가도 필요한 제한을 정하고, 사람과 AI가 실제로 적용됐는지 확인할 수 있도록 돕자는 취지입니다.

## 사람과 업무에 따라 허용할 범위를 정합니다

게스트(비로그인 사용자)도 권한 관리 대상입니다. 예를 들어 공개된 안내와 게시글은 읽을 수 있지만, 회원 전용 글은 볼 수 없도록 정할 수 있습니다. 로그인하지 않아도 이용할 수 있는 정보와 기능을 먼저 구분합니다.

권한을 정하는 기준은 여러 가지이며, 서비스에 맞게 함께 사용할 수 있습니다.

- 맡은 역할: 작성자는 글을 쓰고, 편집자는 글을 검토해 공개합니다.
- 개별 허용: 같은 문서라도 김철수에게는 편집을, 다른 참여자에게는 읽기만 허용합니다.
- 자료와의 관계: 회원은 자신의 주문만 보고, 프로젝트 참여자는 참여 중인 프로젝트의 자료만 봅니다.
- 이용 조건: 자료를 볼 권한이 있는 직원도 회사에서 정한 접속 환경에서만 이용하도록 제한합니다. 회사 내부에서 접속했다는 이유만으로 모든 자료를 허용하지는 않습니다.

읽기·수정·삭제·승인·다운로드·다른 사람에게 권한 주기도 구분합니다. 읽을 수 있다고 수정까지 할 수 있는 것은 아닙니다. "관리자"에게도 맡은 일에 필요한 권한만 줍니다. 게시판을 관리한다는 이유만으로 회원의 결제정보까지 볼 필요는 없습니다.

## 버튼을 숨겨도 실제 요청을 막을 수 있어야 합니다

버튼이나 메뉴를 숨기는 것은 화면에서 이용할 기능을 정리하는 방법입니다. 화면을 거치지 않고 같은 작업을 요청할 수도 있으므로, 숨기는 것만으로 권한을 제한할 수는 없습니다.

서버(서비스의 요청을 처리하는 컴퓨터나 실행 환경)는 요청마다 해당 자료에 그 작업을 할 권한이 있는지 확인해야 합니다. 예를 들어 다른 사람의 글에서 삭제 버튼을 숨겼더라도, 서버가 작성자나 관리 권한을 확인하지 않고 삭제 요청을 처리한다면 제한이 빠진 것입니다.

API는 브라우저나 앱이 서버에 정보나 작업을 요청하고 결과를 받는 통로입니다. 브라우저를 조작하고 요청을 보낼 수 있는 AI 도구도, 페이지와 함께 전달된 코드에서 숨겨진 버튼이나 기능의 동작 방식을 파악해 API를 직접 호출할 수 있습니다. 화면에서 찾기 어렵게 만들거나 관리 화면 주소를 알려주지 않는 것으로는 막을 수 없습니다.

로그인했다거나 화면에서 한 번 확인했다는 이유로 서버의 권한 확인을 생략하지 않습니다. 허용할 근거가 없거나 권한을 확인할 수 없다면 정보를 보내거나 작업을 실행하지 않아야 합니다.

## 볼 수 없는 정보는 브라우저에 보내지 않습니다

자료 하나를 볼 수 있어도 그 안의 모든 항목을 볼 수 있는 것은 아닙니다. 데이터베이스(DB, 정보를 모아 보관하는 저장소)에서는 이름·연락처·결제금액처럼 나뉜 항목을 컬럼이라고 부릅니다. 이런 항목별로도 권한을 정해야 합니다.

예를 들어 주문 조회 담당자에게 주문번호·금액·처리 상태만 허용했다면 연락처와 내부 메모는 보내지 않습니다. 화면에 표시되지 않아도 API 응답(서버가 보내준 결과)에 들어 있다면 이미 이용자의 기기에 전달된 정보이며, 브라우저에서 확인할 수 있습니다. 처음 받은 페이지 안에 보이지 않는 데이터로 넣어 두는 경우도 같습니다.

서버에서 허용된 항목만 골라 보내야 합니다. 전체 자료를 먼저 보내고 브라우저에서 필요 없는 항목을 숨기는 방식으로 대신하지 않습니다.

이름을 일부만 볼 수 있는 담당자에게는 `김*수`처럼 가린 값만 보냅니다. 이를 마스킹이라고 합니다. 원래 이름인 `김철수`를 보내고 화면에서만 가리거나, 다른 항목에 원래 이름을 함께 넣어 두면 보호가 되지 않습니다. 전체 이름은 볼 권한이 확인된 경우에만 전달합니다.

수정할 수 있는 항목도 따로 정합니다. 회원이 자기 소개를 바꿀 수 있다고 회원 등급이나 관리자 여부까지 바꿀 수 있는 것은 아닙니다. 화면에 없는 항목을 바꾸라는 요청이 들어와도 권한이 없다면 반영하지 않습니다.

같은 자료를 검색 결과·상세 화면·다운로드 파일·API에서 제공한다면 모두 같은 권한 기준을 적용합니다. 화면에서는 연락처를 가렸는데 내려받은 파일에는 전체가 들어 있는 경우도 확인해야 합니다.

## DB에서도 필요한 항목만 가져옵니다

DB에 암호화해 보관한 정보도 프로그램에서 사용할 때는 읽을 수 있는 원래 값으로 풀 수 있습니다. 이를 복호화라고 합니다. 예를 들어 연락처를 복호화한 뒤 응답에 담으면 이용자는 원래 연락처를 받게 됩니다. 저장할 때 암호화했다는 사실만으로 조회와 전달까지 제한되는 것은 아닙니다.

쿼리(DB에 자료를 요청하는 내용)에는 주문번호·금액처럼 필요한 항목을 하나씩 지정합니다. 조회할 항목 대신 "전부 가져오기"를 뜻하는 별표(`*`)를 쓰지 않습니다. 화면 표시나 서버의 업무 처리에 필요하지 않은 항목은 처음부터 조회하지 않습니다.

JOIN은 관련 있는 여러 표의 자료를 함께 조회하는 것입니다. 이때도 각 표에서 필요한 항목만 선택합니다. 주문 목록을 보여주려고 주문자 정보를 연결하면서, 필요 없는 연락처와 주소까지 통째로 가져오지 않도록 합니다.

DB 자료를 프로그램에서 다루도록 돕는 도구를 ORM이라고 합니다. JPA를 사용하는 개발 환경에서도 이런 도구를 이용합니다. 설정이나 사용 방식에 따라 관련 자료를 함께 또는 나중에 불러올 수 있으므로, 직접 작성한 쿼리뿐 아니라 도구가 가져오는 자료도 살펴봅니다. 불러온 자료를 그대로 API 응답에 옮기지 않아야 합니다.

권한별로 조회할 항목을 정하는 방법은 언어와 개발 도구에 따라 다릅니다. 하지만 구현과 관리가 번거롭다는 이유로 전체 항목을 가져오지는 않아야 합니다. 서버 내부 계산에 필요한 정보라도 이용자에게 보낼 수 있는지는 별도로 판단합니다.

## AI 에이전트도 누구를 대신해 어떤 일을 하는지 확인합니다

AI 에이전트는 사람의 요청이나 정해진 업무에 따라 도구를 사용해 정보를 조회하고 작업하는 프로그램입니다. 어떤 에이전트가 누구를 대신하는지, 맡은 일과 이용할 자료·항목·기능이 무엇인지 구분해야 합니다.

사용자 대신 일하는 에이전트는 그 사용자의 권한과 맡긴 일의 범위를 모두 지켜야 합니다. 예를 들어 주문 상태 확인을 맡겼다면 다른 회원의 주문을 조회해서는 안 됩니다. 사용자에게 주문 취소 권한이 있더라도, 상태 확인만 맡겼다면 에이전트가 임의로 주문을 취소해서는 안 됩니다.

운영용 에이전트도 업무를 맡긴 사람이나 조직, 허용한 범위가 분명해야 합니다. 서버 상태를 살피는 에이전트에게 고객 개인정보 전체를 읽거나 회원 등급을 바꾸는 권한까지 주지 않습니다. 민감한 원본 정보는 기본적으로 접근 대상에서 제외하고, 필요한 정보도 민감한 부분을 가리거나 건수·합계로 제공하는 방향입니다.

AI에게 "업무 범위를 넘지 마세요"라고 지시하는 것만으로는 부족합니다. 서버와 작업을 실행하는 도구가 실제로 권한을 확인해야 합니다. 에이전트가 말하는 사용자 이름이나 "허락받았다"는 설명만 믿지 않고, 서비스가 확인한 사용자와 맡긴 일을 기준으로 제한합니다. 사용자 대신 일하는 에이전트가 운영용 권한을 이용해 이 제한을 넘어서도 안 됩니다.

## 권한이 필요 없어진 뒤에는 거두고, 변경을 기록합니다

담당 업무가 바뀌거나 프로젝트 참여가 끝나면 이전 권한을 거둡니다. 임시 권한은 언제 끝낼지 정하고, 이미 로그인한 상태에서도 변경 이후의 요청이 제한되는지 확인합니다. 에이전트도 맡긴 일이 끝나거나 사용자의 권한이 바뀌면 이후 요청에 반영해야 합니다. 이미 전달하거나 내려받은 정보까지 자동으로 되돌릴 수 있는 것은 아닙니다.

권한을 주거나 바꾼 사람·시점·이유를 기록하고, 권한을 줄 수 있는 담당자도 제한합니다. 에이전트의 작업은 어떤 에이전트가 누구의 요청이나 어떤 운영 업무로, 어떤 자료에 무슨 일을 했고 결과가 어땠는지 남깁니다. 사람이 직접 한 일과 대신 수행한 일을 구분하되, 개인정보 원문을 기록에 그대로 복사하지 않습니다.

## 허용되는 경우와 거부되는 경우를 함께 점검합니다

관리자 계정으로 기능이 작동하는지만 확인하지 않습니다. 게스트·일반 회원·업무별 담당자·에이전트로 나누어, 허용된 일은 할 수 있고 허용되지 않은 일은 거부되는지 확인합니다. 실제 개인정보를 불필요하게 사용하지 않도록 점검용 사용자와 자료를 준비할 수 있습니다.

공통으로 확인할 항목입니다.

- [ ] 누가 어떤 자료와 항목을 보고, 어떤 작업을 할 수 있는지 정했는가?
- [ ] 게스트에게 공개한 기능은 작동하고, 회원 전용 정보와 기능은 제한되는가? 비로그인 상태와 로그아웃 후의 상태를 모두 확인했는가?
- [ ] 버튼이나 화면을 거치지 않은 요청도 서버에서 권한을 확인하는가?
- [ ] 화면뿐 아니라 실제로 전달된 데이터에도 권한 없는 정보가 포함되지 않는가?

사용하는 기능에 따라 추가할 항목입니다.

- [ ] 회원별·조직별 자료가 있다면: 허용받지 않은 다른 회원이나 조직의 자료에 접근할 수 없도록 구분했는가?
- [ ] DB를 조회한다면: "전부 가져오기" 대신 필요한 항목을 지정하는가? JOIN·ORM으로 함께 가져오는 자료도 확인했는가?
- [ ] 암호화하거나 가린 정보가 있다면: 복호화한 원본은 허용된 사람에게만 보내고, 일부만 볼 수 있는 사람에게는 가린 값만 보내는가?
- [ ] 검색·다운로드 등 여러 경로가 있다면: 각 경로에 같은 권한 기준을 적용했는가?
- [ ] 권한을 바꾸거나 일을 맡긴다면: 변경·종료 이후의 요청에도 제한이 반영되고, 담당자와 변경 이유를 확인할 수 있는가?
- [ ] 사용자 대신 에이전트가 일한다면: 해당 사용자의 권한과 맡긴 일의 범위를 모두 지키는가?
- [ ] 운영용 에이전트가 있다면: 맡은 업무 밖의 자료·기능과 민감정보 원문에 접근하지 못하는가? 수행한 작업을 기록으로 확인할 수 있는가?

점검을 돕는 AI도 허용된 범위에서 확인해야 합니다. 먼저 코드(프로그램을 작성한 내용)와 설정을 살펴보고, 어떤 자료를 조회·복호화해 전달하는지 확인합니다. 그다음 "문의 담당자가 연락처 전체를 봐야 하는가"처럼 운영자가 결정할 사항이나 자료가 없어 확인할 수 없는 부분만 질문하도록 합니다.

결과에는 확인한 역할·자료·항목·작업과 확인하지 못한 부분을 남깁니다. 화면만 보고 실제 전달된 데이터를 확인하지 못했다면 점검을 마쳤다고 표시하지 않습니다.
